# V2 Mira Voice And Avatar Roadmap

## Purpose

This roadmap describes future voice and visual persona capabilities for Mira Vale and the broader OneSmarter agent team.

The scripted voice sample prototype is now implemented on `/ai-agents` as a frontend-only section with transcripts and controls for approved static audio assets. All five scripted samples are wired for playback from `public/audio/mira/` under the approved `mira-v1` voice identity. This does not add voice API calls, SDKs, API keys, audio recording, microphone permissions, browser speech capture, live text-to-speech, speech-to-text, realtime voice, avatar/video implementation, uploads, or endpoint behavior changes.

Current Mira status:

- Mode: `local_harness_mock`.
- Text input only.
- Approved public knowledge base retrieval.
- Safety flags and claim-boundary rules.
- Privacy reminders.
- No real model call.
- No audio capture.
- Scripted voice sample UI with all five approved static MP3 files enabled.
- No uploads.

Future voice and persona work may eventually apply to multiple OneSmarter agents, including Maya Renshaw as a possible intake/routing voice. Mira remains the first voice candidate because she already has the approved public-knowledge mock endpoint and safety harness.

## 1. Voice Vision

Mira's future voice layer should make the guide feel more natural while staying professional, controlled, and clearly bounded.

The long-term vision includes:

- Voice output so Mira can speak approved, grounded answers.
- Optional speech input for visitors who prefer to ask aloud.
- Persona-aligned tone: warm, clear, composed, and concise.
- Limited multilingual demonstrations where appropriate, especially for simple service explanations or greetings.
- Accent or style choices only when they are clearly presented as interface preferences, not human impersonation.
- A professional presentation style that supports trust, accessibility, and clarity.

Voice should remain an interface layer over Mira's governed behavior. It must not bypass the approved knowledge base, claim rules, privacy warnings, handoff behavior, or safety checks.

## 4. Consent And Privacy Requirements

Before any public voice feature:

- Microphone permission must be explicit and user-initiated.
- Voice use must show a clear warning before activation.
- No audio recording by default.
- No PHI, confidential documents, private operational details, credentials, or regulated data should be submitted.
- The UI must explain whether speech is transcribed, whether transcripts are logged, and who can access them.
- A retention policy is required before production.
- Privacy Policy updates are required before public launch.
- Terms and privacy language should be reviewed before enabling microphone or speech processing publicly.
- If regulated workflows are ever in scope, legal/security review must decide whether additional contractual controls are required.

Recommended default for early phases:

- Do not store raw audio.
- Do not log full transcripts by default.
- Log only safe operational metadata unless a reviewed quality process requires limited transcript samples.
- Route business-specific, security, procurement, legal, medical, or regulated-workflow questions to care@onesmarter.com.

## 5. Accessibility Requirements

Voice must be additive, not required.

Requirements:

- Text input must remain available.
- Captions or transcripts must be available for spoken output.
- Users must be able to mute Mira.
- Users must be able to stop playback.
- Users should be able to replay spoken answers only when appropriate.
- Keyboard users must be able to operate voice controls.
- Screen readers should receive equivalent text content and control labels.
- Avatar or visual effects must respect reduced-motion preferences.
- Voice status should be visible, such as idle, listening, processing, speaking, muted, or unavailable.
- Errors should provide a text fallback and a human handoff path.

## 6. Safety Requirements

Voice must not override Mira's existing guardrails.

The same rules apply:

- Answer only from approved OneSmarter content in early releases.
- Use the same knowledge base and claim-boundary rules.
- Do not provide legal advice.
- Do not provide medical advice.
- Do not guarantee compliance.
- Do not make unsupported HIPAA, SOC 2, ISO, PCI DSS, security, privacy, or certification claims.
- Sensitive, PHI, confidential, or business-specific questions should hand off to care@onesmarter.com.
- Rate limiting and abuse protection must cover voice input and audio generation.
- Logging must avoid raw audio, confidential content, and unnecessary transcript storage.
- Prompt injection and instruction-override attempts must continue to be detected and refused.

Additional policies needed before realtime or open-ended voice:

- Crisis/high-risk handling policy.
- Abuse and harassment handling.
- Repeated-call or automated-calling protection.
- Cost and quota controls.
- Security review of audio transport, retention, and vendor processing.

## 7. Avatar And Visual Persona Roadmap

Mira's visual persona should communicate agent presence without pretending to be a real person.

The `/ai-agents` page now includes a static visual-presence prototype for Mira. It maps the existing conversation posture to one of six approved static visual states: welcoming, helpful, thoughtful, careful, concerned, and confident. The Welcoming portrait is approved under identity profile `mira-visual-v1` and acts as the visual identity baseline. The other five states still use a branded local placeholder with `MV` initials, posture text, and accessible descriptions until matching artwork is approved.

This static visual layer does not add camera access, facial tracking, lip-sync, generated video, runtime image generation, realtime avatar services, microphone input, speech recognition, or live animation.

Future Helpful, Thoughtful, Careful, Concerned, and Confident portraits should use the same person, framing, lighting, wardrobe family, and background style as the approved Welcoming portrait.

Recommended progression:

| Stage | Capability | Notes |
| --- | --- | --- |
| A1 | Static persona card | Implemented: static visual-presence placeholder with controlled posture states. |
| A2 | Expression-state prototype | Show simple states such as welcoming, thinking, reviewing, handoff, and unavailable. |
| A3 | Simple animated visual state | Add restrained motion for state changes, respecting reduced-motion settings. |
| A4 | Agent-world scene concepts | Prototype coffee-break, chess, operations-room, trust-review-table, and agent-feed scenes as conceptual visual environments. |
| A5 | Later video/avatar scene | Consider a stylized non-human-deceptive avatar or scene-based presentation only after accessibility, consent, and trust review. |

Guidelines:

- Do not present Mira as a real human.
- Do not create a deepfake-like or human-deceptive experience.
- Keep the visual language custom, branded, and clearly software-based.
- Avoid over-animated or entertainment-first presentation for enterprise/security contexts.
- Make the visual state support comprehension, not distract from the answer.
- Future animated avatar work requires separate privacy, accessibility, performance, safety, vendor, and production review.

### Mood Signal and Expression State Layer

The `/ai-agents` page now includes a deterministic Mood Signal panel beside the Mira conversation experience. It shows the current controlled presentation state using labeled bars for welcoming, curious, helpful, thoughtful, careful, concerned, and confident.

The current implementation is frontend-only and derives state from existing response metadata. It does not ask a model to invent emotions, does not add animation, and does not introduce voice, video, microphone, or avatar behavior.

Possible expression states:

- Blink
- Smile
- Serious look
- Eyebrow raise
- Eyebrow pucker / concerned look
- Pondering look
- Attentive eye movement

Requirements:

- Respect reduced-motion preferences.
- Keep expressions restrained and professional for enterprise contexts.
- Provide a text fallback that describes the current state for accessibility.
- Do not require animation for the first prototype.
- Do not imply the agent has unbounded emotion or human-like awareness.

Future implementation path:

| Phase | Scope |
| --- | --- |
| Mood P1 | Implemented: deterministic mood-signal panel in `/ai-agents`. |
| Mood P2 | Implemented: derive mood state from endpoint metadata such as `riskFlags`, `confidence`, and `handoffNeeded`. |
| Mood P3 | Implemented in lightweight form: simple expression-state visual without video/avatar implementation. |
| Mood P4 | Connect expression state to future voice/avatar behavior. |
| Mood P5 | Allow real LLM output to propose a `presentationState` only after strict allowed-value validation. |
